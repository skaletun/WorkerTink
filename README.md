# WorkerTink 2.10.0

**WorkerTink** — локальный PWA для рабочего календаря, смен, зарплаты, отпусков, больничных и заметок по сменам.

Приложение работает офлайн, устанавливается как PWA и может размещаться на GitHub Pages. Основной профиль хранится локально на устройстве; backend для работы приложения не нужен.

## Возможности

### Рабочий календарь

- графики `5/2`, `4/1`, `3/2`, `3/1`, `6/1`, `2/2`, `7/0`;
- дневные и ночные смены;
- `2/2`: День/День, День/Ночь, Ночь/Ночь;
- `7/0`: День, Ночь или Сутки;
- для `7/0` задаётся непрерывный период вахты от 1 до 6 месяцев; после окончания выбранного периода календарь показывает выходной период до следующей даты начала;
- дата начала — реальная точка отсчёта цикла, без захардкоженных дат;
- даты до выхода на работу отображаются как «До начала» и не открываются для редактирования;
- ручная замена отдельной смены;
- заметки прямо на конкретной дате;
- федеральные праздники и известные переносы для поддерживаемых годов;
- настраиваемый коэффициент праздничной доплаты.

### Расчёт зарплаты

Расчётное ядро разделяет:

- плановые часы по графику;
- фактически отработанные плановые смены;
- дополнительные смены, добавленные вручную в выходной по графику;
- праздничные часы;
- ночные смены;
- отпускные;
- больничные;
- НДФЛ;
- аванс и остаток.

Для смен `День` и `Ночь` используется 8 часов, для `Сутки` — 24 часа. Ночная доплата настраивается отдельно; по умолчанию установлено 20%. Фактический размер доплаты зависит от условий работодателя.

Аванс по умолчанию равен 50% указанного оклада и может быть переопределён отдельно для любого месяца. Это модель планирования, а не утверждение о фактическом порядке выплат конкретного работодателя.

### Отпуск и больничные

- периоды отпуска и больничного хранятся отдельно;
- праздничные дни внутри ежегодного отпуска не расходуют дни отпуска;
- дни отсутствия исключаются из обычной оплаты смен;
- отпускные используют средний доход за доступную историю 12 месяцев;
- больничные используют доступную историю 24 месяцев и коэффициент по стажу: `<5` лет — 60%, `5–8` — 80%, `8+` — 100%.

Расчёты отпуска и больничного остаются пользовательской моделью и не заменяют расчёт работодателя: конкретные правила зависят от условий трудового договора, локальных актов и применимого законодательства.

### Визуальный редактор заметок

Редактор заметок работает как WYSIWYG-редактор:

- текст форматируется и отображается сразу;
- нет отдельного окна предпросмотра;
- жирный, курсив, заголовки, списки, цитаты, код и ссылки;
- создание и редактирование Markdown-таблиц;
- ПК: `Ctrl/Cmd+B`, `Ctrl/Cmd+I`, `Ctrl/Cmd+K`, `Ctrl/Cmd+Shift+7`, `Ctrl/Cmd+Shift+8`, `Ctrl/Cmd+Shift+X`;
- мобильная toolbar-панель с постоянно видимыми кнопками форматирования;
- заметка хранится как Markdown и может экспортироваться в `.md`;
- общий импорт/экспорт заметок сохраняет структуру `## SHIFT: YYYY-MM-DD`.

Markdown-адаптер является намеренно ограниченным форматом редактора: заголовки, списки, цитаты, код, ссылки, базовое inline-форматирование и таблицы. Сложный произвольный Markdown вне этого набора не гарантируется.

### Данные и восстановление

- основной профиль хранится в `localStorage`;
- формат профиля имеет версию схемы и последовательную нормализацию при загрузке;
- старые ключи `v2`/`v3` читаются автоматически;
- импорт JSON проходит через ту же нормализацию, что и обычная загрузка;
- при повреждённом профиле исходный JSON пытается сохраниться в recovery-снимок перед переходом к безопасному профилю по умолчанию;
- экспорт JSON предназначен для резервной копии.

Для долгосрочного хранения больших объёмов заметок в будущем может потребоваться переход с `localStorage` на IndexedDB. Текущая версия сохраняет совместимость с существующим форматом профиля.

## Directory API

Запуск локального каталога:

```bash
npm run api
```

По умолчанию API работает на `http://localhost:8787`. Для frontend задайте переменную окружения:

```text
VITE_WTINK_DIRECTORY_URL=https://your-api.example.com
```

Для GitHub Pages workflow уже читает GitHub Actions **Repository Variable** `WTINK_DIRECTORY_URL`. Создайте её в **Settings → Secrets and variables → Actions → Variables**. Пример локальной конфигурации находится в `.env.example`, подробности — в `server/README.md`.

## GitHub Pages

Vite использует относительный `base: './'`, поэтому приложение подходит для репозитория вида:

```text
https://username.github.io/WorkerTink/
```

В репозитории есть `.github/workflows/deploy.yml`. Workflow запускается после push в `main`, устанавливает зависимости, выполняет тесты и production build, после чего публикует `dist` через GitHub Pages.

Перед первым deployment в GitHub откройте:

**Settings → Pages → Source → GitHub Actions**.

## Offline / PWA

WorkerTink не требует сервера для хранения профиля. Service Worker кэширует production-ресурсы через `vite-plugin-pwa`, а профиль сохраняется локально.

После обновления версии PWA использует `registerType: 'autoUpdate'` и очищает устаревшие cache entries.

## Ограничения расчётов

WorkerTink — планировщик и расчётный инструмент, а не бухгалтерская система. Зарплата, отпускные и больничные могут зависеть от системы оплаты труда, локальных актов, фактических начислений, региональных условий и действующего законодательства.

Приложение специально показывает модель расчёта, а не выдаёт её за официальный расчёт работодателя.

## Таблицы в заметках

WYSIWYG-редактор поддерживает адаптивные Markdown-таблицы. На мобильных таблица ужимается по ширине окна с переносом длинного содержимого; горизонтальный скролл не требуется. Последняя строка таблицы используется как постоянная строка ввода и не сохраняется в Markdown. После заполнения последней строки редактор автоматически создаёт следующую. На ПК ПКМ по таблице открывает меню добавления строки/столбца и удаления; на мобильных устройствах те же действия доступны долгим нажатием.

## Профиль, WTinkID и P2P

Перед мастером настройки новый пользователь проходит локальную регистрацию: имя, должность и аватар. После неё доступна отдельная страница профиля.

Каждому профилю назначается короткий публичный идентификатор вида `WTinkID-592391`. В разделе «Друзья» можно найти пользователя по этому ID и отправить заявку. Входящие заявки находятся во вкладке «Заявки в друзья», а отправленные — во вкладке «Исходящие заявки». Получатель может принять или отклонить входящую заявку; при принятии профиль добавляется в локальный список друзей.

Для поиска пользователей нужен Directory API. Production-реализация находится в `directory-api/` и работает на Cloudflare Workers + D1. Старый `server/index.mjs` оставлен только как legacy/local fallback. Чаты и заметки сервер не хранит.

В чате доступны специальные карточки:
- **Профиль** — передача рабочей карточки с возможностью активировать её как друга прямо из чата.
- **Заметка** — передача заметки смены вместе с датой; получатель может активировать её непосредственно на указанную дату календаря.

Сам чат и содержимое заметок передаются через WebRTC DataChannel и сохраняются локально в `localStorage`. После принятия заявки P2P-соединение устанавливается автоматически через короткоживущую signaling-сессию в Directory API; ручной обмен кодами больше не нужен.

## Directory API: Cloudflare Workers + D1

Для реального поиска пользователей по `WTinkID` и межустройственных заявок в друзья WorkerTink использует отдельный Directory API. Основное приложение и P2P-чаты при этом не требуют собственного backend: каталог хранит только публичные профили и статусы заявок.

Готовая production-реализация находится в `directory-api/`:

```text
Cloudflare Worker
      │
      └── D1 (SQLite)
          ├── profiles
          └── friend_requests
```

### Быстрый запуск

1. Создайте аккаунт Cloudflare.
2. Установите Node.js 16.17+.
3. Перейдите в `directory-api`.
4. Выполните `npm install` и `npx wrangler login`.
5. Создайте D1:

```powershell
npx wrangler d1 create workertink-directory --location weur
```

6. Вставьте полученный `database_id` в `directory-api/wrangler.jsonc`.
7. Примените миграции:

```powershell
npx wrangler d1 migrations apply workertink-directory --remote
```

8. Выполните деплой:

```powershell
npx wrangler deploy
```

9. Проверьте:

```text
https://ВАШ-WORKER.workers.dev/health
```

10. В GitHub Pages создайте repository variable `WTINK_DIRECTORY_URL` со значением URL Worker.

Полная пошаговая инструкция, включая CORS, API-токены GitHub Actions, миграции и диагностику, находится в [`directory-api/README.md`](directory-api/README.md).

Для CI/CD также добавлен `.github/workflows/deploy-directory.yml`. Он применяет неприменённые D1-миграции и публикует Worker при изменениях в `directory-api/`. Для него нужны GitHub Secrets `CLOUDFLARE_API_TOKEN` и `CLOUDFLARE_ACCOUNT_ID`.

## Push-уведомления

В версии 2.9.0 WorkerTink поддерживает Web Push. В настройках можно включить уведомления и отдельно управлять категориями. Сервер хранит техническую push-подписку и минимальный набор дат для доставки напоминаний; рабочие расчёты, заметки и полный календарь остаются локальными.

Для production в Cloudflare Worker нужны secrets `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` и `VAPID_SUBJECT`. Дополнительные GitHub Actions secrets для VAPID не требуются, если secrets уже установлены через Wrangler: они хранятся в самом Cloudflare Worker.


### Аккаунт и вход
- Полная регистрация аккаунта через WTinkID + обязательный PIN из 6 цифр.
- PIN хранится в каталоге только как криптографический хэш; после пяти неверных попыток вход временно блокируется.
- Добавлен вход по WTinkID + PIN на новом устройстве и после выхода из аккаунта.
- Добавлен необязательный OnePass на базе passkey/WebAuthn: включается только вручную в настройках, не предлагается во время регистрации.
- Настройки безопасности собраны в компактном верхнем блоке; выход из аккаунта не удаляет локальные рабочие данные.
